  - The DR-2 branch `if (work.IsCompletedSuccessfully && work.Result.Failure is null)` (`src/Ingestion/Scheduling/IngestionScheduler.cs:698`, executed immediately after `attemptCts.Cancel()` at :688) observes the step's terminal state **only if the step's continuation resumed inline on the cancelling thread**.   - Consequences: **two `ingest_runs` rows for one attempt, a spurious `RUN_HUNG` alert, and a spurious retry.**

- **Pinned design (planner; candidate shapes evaluated, one chosen):** a **bounded post-cancel settle window on the scheduler clock** — the review's shape (a). In the hung path (a bound fired, host not stopping), after `attemptCts.Cancel()` + `await deadlineCts.CancelAsync()`, race `work` against a clock-driven settle delay (`Ingestion:Scheduler:PostCancelSettleWindow`, code default **5 s**, `<= 0` disables — documented, mirroring the bounds' disable semantics; mis-typed huge values ride 059's DR-1 failed-attempt path since the delay is created inside the classifying `try`):
  - `work` completes within the window **and** `IsCompletedSuccessfully && Failure is null` → the terminal truth (the existing DR-2 branch's semantics, now holding for the *whole* cancel window instead of only the inline-resume interleaving): one row (the step's own), no `RUN_HUNG`, no alert, no retry. A work that completes within the window but carries a `Failure` still goes hung — the "a chain that merely *ended* on our own cancellation is not a success" doctrine is unchanged.
  - the window elapses first → the existing hung path **unchanged**: exactly one `RUN_HUNG` row + one alert naming the pre-cancel step (DR-3), the ladder takes over, `DisposeWithAbandonedWork` disposal unchanged. The row/alert/log state the grace honestly: `stats_json.settleWindowSeconds` additive, and the error/alert text mentions the elapsed post-cancel settle window so an operator knows it was given.
  - The host-stop path (checked before the settle) is untouched: a stopping host still unwinds with no row, no alert (DR-5b).
  - **Why (a) over (b) — the single per-attempt claim:** the defect is an *observation* race, not a *write* race — the step's terminal state exists but the single synchronous re-check cannot see a queued continuation. The settle window fixes the observation, which fixes **all three** consequences (double row, spurious alert, spurious retry). A claim shared by the runner's terminal row and the watchdog row (shape (b), threaded through `IngestionRunContext` into `IngestionJobRunner.RecordAsync`) makes the row write *exclusive* but does not decide *truth*: when the watchdog wins the claim, a genuinely-completed step is still recorded hung, its own truthful row is suppressed (the step's data **was** written — suppressing its row removes real information), and the spurious alert + spurious retry persist. Shape (b) is therefore recorded as the **fallback, already in this ticket's scope** (`src/Ingestion/Jobs/Jobs.cs`): if implementation shows the settle window cannot close a demonstrated residual, the claim lands in-scope rather than as a review-gate block. **Residual of (a), recorded honestly:** a cancellation-swallowing step completing *after* the window still lands its row beside `RUN_HUNG`. In production the runner writes through the attempt token (`SaveChangesAsync(cancellationToken)` — a token-cancelled EF write throws and `RunCoreAsync` rethrows OCE unrecorded), so the production shape writes no second row; the residual is reachable only through cancellation-swallowing steps, and for them the `RUN_HUNG` row naming the step that exceeded its bound *plus* the grace window is the honest attempt record. If this residual ever shows live, shape (b) is the recorded durable follow-up.
