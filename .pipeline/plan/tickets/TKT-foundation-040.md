# TKT-foundation-040: morning-cadence ingest chain (~08:30 Istanbul, trading days) — EOD-repair safety net + incremental KAP freshness; never newer market prices

- Status: done
- PR: https://github.com/sarperim/degerli/pull/110
- Size: M
- **Priority: P2 — dispatch-ready; user-approved product change (2026-10-20 morning check: "we can take data morning and night").** Code-disjoint from the 036–039 wave and from PR #106's `KapSources.cs` lane; may dispatch in parallel with them.
- User intent (recorded): a morning chain alongside the existing 20:30 EOD chain that (a) **retries/repairs the previous night's EOD** if it failed or partially ran — today's retry ladder is +5/+15/+60 min (scheduler `RetryDelays`), exhausting by ~21:50, so a failed night currently leaves the site serving yesterday-before-yesterday until the next 20:30; (b) refreshes the **KAP lanes** (statements now; dividends/corporate-actions/disclosures once TKT-foundation-034 lands — disclosures are published intraday, so a morning pass catches overnight/early-morning ones); (c) leaves macro alone (macro-daily already runs 08:00; macro-cpi 09:30).
- **Honest constraint (encoded in the design, never implied away): BIST price data is EOD.** A morning run on Tuesday at 08:30 targets **Monday's session** (the previous trading day) — Tuesday's session does not exist until the ~18:00 close and is owned by the 20:30 chain. The morning chain is **catch-up + KAP freshness, NOT newer market prices**; no doc, log line, or UI implication may suggest otherwise.
- **Live evidence this is needed (dev ledger, 2026-10-19/20, read-only):** Monday's scheduled 20:30 Istanbul chain wrote `prices succeeded 17:30:00 UTC` and then produced **no statements/metrics-recompute/snapshot/medians rows in its wake** — the Monday overview row exists only because the orchestrator admin-triggered `market-snapshot` run 101 at 18:33 UTC. The user's Tuesday-morning site visit was one missed admin trigger away from an `unavailable` front page. (The stall's root cause is NOT investigated or claimed here — out of scope; the morning pass is the safety net either way. Also live-verified: the three event-family jobs fail in ~1 s each on their placeholder KAP paths — the known pre-034 lane — which is why they are phase 2.)
- Scheduler grounding (studied, `src/Ingestion/Scheduling/`): one shared EOD stream (`IngestionSchedulerOptions.Cron` = `0 30 20 * * *` Europe/Istanbul, `TradingDaysOnly`, running the pinned `EodIngestChain`: prices → statements → dividends → corporate-actions → disclosures → metrics-recompute → market-snapshot → sector-medians, fail-stop on `Failed`) plus per-job `JobSchedules` streams (macro-daily 08:00, macro-cpi 09:30, funds 19:00–19:10, not trading-day gated). `NextWake`/`TickAsync` are pure decisions over a supplied instant — **deterministic under a fake clock** (the L2 testability seam this ticket's criteria use). Streams hold in-memory state; the durable record is the `ingest_runs` ledger.
- Scope:
  1. **A second chain stream:** the scheduler supports a morning chain — `Ingestion:Scheduler:MorningCron` (shipped `appsettings.json` = `0 30 8 * * *`; empty code default = no morning stream (test/composition contract), same `TimeZone`), trading-day gated, running a new pinned **`MorningIngestChain`** (the `EodIngestChain` sibling convention). Recommended shape: a `RunDateMode` on the stream — the EOD stream resolves `runDate = occurrence date`; **the morning stream resolves `runDate = the previous trading day** (weekday-backing via the existing `IIngestionCalendar`, the same limitation every stream has; the jobs' own stored-facts resolution self-heals, the 028 doctrine). Implementation latitude inside these pinned semantics (dedicated options + pinned class, or a generalized `ChainSchedules` list) is the coder's; existing options/behavior for the EOD and per-job streams stay byte-compatible.
  2. **Phase 1 composition (dispatchable now):** `prices (repair-gated) → statements (incremental) → metrics-recompute → market-snapshot → sector-medians`. **The prices repair gate is stored-prices-as-truth** (the §10.9.13 doctrine): the gate skips the prices job when every current constituent of the bound universe already has a `daily_prices` row for the target day — a fully-covered day is never re-fetched, so a normal morning generates **zero** İş Yatırım calls and zero `CONFLICTING_VALUE` quarantine noise (the 74k-row/TKT-foundation-035 lesson); an uncovered/partial day runs the job at the existing pacing (`RequestDelayMs`; the 3 s live lesson is operational, not code). Statements' per-company cursors (§10.9.11) make the morning pass incremental (~1 paced list call per XU030 company). metrics-recompute/market-snapshot/sector-medians are idempotent by existing contract (recompute from stored facts; snapshot one-row-per-day no-op) — they close the loop so a failed night yields a served overview row by ~09:00.
  3. **Phase 2 (explicitly gated on TKT-foundation-034 / PR #106 merging — a phased dependency inside this ticket, not a second ticket):** add `dividends → corporate-actions → disclosures` to the morning chain between statements and metrics-recompute (mirroring `EodIngestChain` order). Until 034 lands they are NOT morning-chain members — they fail fast on the placeholder paths (live-verified) and would poison the chain's fail-stop. Post-034, their per-family per-company cursors make the morning pass incremental; **the morning pass is never a full-universe first pull** (034's ~1k-call disclosures pass belongs to the EOD chain/backfill, never to 08:30). All KAP calls ride the existing `KapRequestPacer` (≥12 s, 401-penalty-box aware) — unchanged.
  4. **Retry + alerting:** the morning stream uses the existing `RetryDelays` ladder and `RETRIES_EXHAUSTED` alert machinery unchanged.
  5. **Docs:** `01` new §10.9.16 (morning-chain doctrine: run-date = previous trading day, repair gate, incremental-only KAP, the EOD honesty constraint) + §13.1 row (next free version after 038's v1.5.14 → **v1.5.15**); `03` §9 gains the morning-chain operations row; test plan `market-data-foundation.md` gains **TC-MDF-077/078** (delivery-planner-applied, test-planner confirmation pending — the v1.2/v1.3 precedent).
