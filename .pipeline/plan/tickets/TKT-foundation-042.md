# TKT-foundation-042: market-snapshot honesty + repairability — same-day recompute must repair a broken row (no SQL surgery), and missing index levels must degrade to honest nulls (never fabricated 0.0000)

- Status: todo
- Size: M
- **Priority: P2 — dispatch-ready** (code lane disjoint from 039/040-in-review and 041's scheduling lane; see Dependencies for the §13.1 serialize note).
- Verified evidence (dev stack, 2026-10-20 evening, orchestrator's repair sequence):
  - **B — same-day re-run is a no-op that won't repair:** after index levels landed (universe-sync run 122), re-running `market-snapshot` returned `written:0, unchanged:0, quarantined:0` and left the existing 2026-10-20 row untouched (`xu100_level = 0.0000`). The orchestrator's only workaround was DELETEing the row and re-running (run 124 then wrote 1 with correct levels) — **operational repair currently requires SQL surgery.** Root: `MarketSnapshotJob`'s resolved-day no-op guard ("a completed day is never recomputed/rewritten", §10.9.13/TC-MOV-005) ignores whether the row's INPUTS have changed since it was written.
  - **C — dishonest zero index levels:** the first Tuesday snapshot (run 120, computed before universe-sync landed the day's levels) wrote `xu100_level = 0.0000 / xu30_level = 0.0000` and the overview SERVED those zeros (the UI would render 0,00). Root (planner-located): `MarketSnapshotEngine.ReadIndexMovesAsync` falls back to `new IndexMove(0m, 0m)` when no index-level row exists for the date (lines ~244, ~263-264), and `MarketAggregates.Compute` copies that zero into the non-nullable `Xu100Level`/`Xu30Level` snapshot columns. **Missing input must degrade honestly, never fabricate 0 — the same honesty class as the 031 decoupling (§10.9.14) and the M-1/BR-RES-008 doctrine.**
- Scope:
  1. **Honest index levels (C):** a snapshot whose index levels for the resolved day are missing computes and serves the indices block as an honest empty — recommended shape: `xu100_level`/`xu30_level` (+ their change columns) become **nullable** (`02` §3.2 migration, the nullable-P/E precedent; existing rows keep their values), the engine returns null moves instead of `(0m, 0m)`, and `GET /market/overview` serves `indices: null` (already contracted — `MarketOverviewResponse.indices` is `{...} | null` and the Web already renders the honest `Unavailable` block for null indices; no Web change). The breadth/movers/volume blocks keep serving (price-derived, §10.9.14) — a missing index level must not take the row down.
  2. **Repairable same-day recompute (B):** the resolved-day guard becomes **input-aware**: recompute the day's aggregate from current facts and compare — identical values → honest `unchanged: 1` (today's `unchanged: 0` on an existing row is itself a counting lie); different values → **overwrite the row in place** (still exactly one row per trading day, `02` §3.2 preserved) and report a new named stat (e.g. `rewritten`) so the ledger shows the repair happened. Historical days (< the resolved day) stay immutable. This amends the §10.9.13 sentence "a completed day is never recomputed/rewritten" to "…never *blindly* rewritten; a same-day recompute with changed inputs repairs the row in place and counts it". Rejected alternative (recorded): admin-only forced delete+recompute — keeps SQL surgery as the only repair path.
  3. **Docs:** `01` §10.9.13 amend (repairable same-day recompute) + §10.9.14 extension (honest index-level empty state) + §13.1 **v1.5.18**; `02` §3.2 amend (nullable index-level columns); test plan TC-MOV-034/035 (delivery-planner-applied, test-planner confirmation pending).
- Traces to: FR-MOV-001 (index levels + change — the honest-null path), FR-MOV-010/NFR-MOV-001 (the served row must be truthful), BR-MOV-009 (snapshot from canonical facts — a recompute with changed facts is still canonical), `01` §10.7 honest-state (0.0000 is a fabricated value); TC-MOV-005 (one-row-per-day — preserved, semantics amended), TC-MOV-012 (payload asOf/state/indices); foundation pseudo-domain convention (post-merge honesty/repair defect — explicit criteria; the 031 precedent).
- Acceptance: **explicit criteria; L2 doubles only.** **(i) Red→green honest indices (TC-MOV-034):** a world with prices but NO index levels for the day → the snapshot row writes with `xu100_level`/`xu30_level` NULL (red today: 0.0000) and `GET /market/overview` serves `state: available`, `indices: null`, real breadth/movers/volume; after levels land, the next run repairs the row (see ii) with real levels. **(ii) Red→green same-day repair (TC-MOV-035):** an existing row for the resolved day + changed inputs (e.g., index levels or prices landing after the first compute) → re-run reports `rewritten: 1` and the row/served payload carry the corrected values (red today: `written:0, unchanged:0`, row untouched); unchanged inputs → `unchanged: 1` (red today: 0), exactly one row per day in both cases; a historical day's row is never touched. **(iii) Golden stability:** TC-MOV-001..005, TC-MOV-029/030 and the `MarketEndpointsTests` payload goldens re-run green with the pre-listed deltas only (the no-op test's expectation becomes input-aware; the FU world always has levels and unchanged inputs, so values are byte-identical). **(iv) Migration:** the nullable-columns migration applies cleanly; existing rows (incl. the dev stack's real 2026-10-19/20 rows) keep their values. **(v) CI green.** **Live criterion (orchestrator post-merge, read-only, no pacing constraint — stored facts only):** after merge, on the dev stack the existing 2026-10-20 row (written via SQL-surgery repair) still serves correctly (`unchanged: 1` on a re-run — the honest count), and a deliberately stale-inputs scenario is repaired by a plain re-run with `rewritten: 1` — attempt/result recorded on the ticket, never fabricated.
