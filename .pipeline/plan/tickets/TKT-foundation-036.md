# TKT-foundation-036: percentage display 100× defect — every `changePct`-class fraction rendered through the no-×100 formatter; fix the unit contract systematically across the Web layer

- Status: done (PR #108 — Web-side fraction×100 fix; Web unit 23/23 + formatter red→green recorded in the PR; E2E value assertions land in the CI e2e job; live criterion pending orchestrator post-merge)
- PR: https://github.com/sarperim/degerli/pull/108
- Size: M
- **Priority: P1 — dispatch immediately.** Home-screen, user-visible wrong numbers (user morning check 2026-10-20, `run-report.md` §"Morning check"): the overview ("Piyasa Genel Görünümü") renders AGHOL "+0,01%" (real: +1,47%), TCKRC "−0,10%" (real: −10% limit-down), BIST 100 "−0,02%" (real: −2,49%), BIST 30 "−0,02%" (real: −2,31%). The user concluded "the data seems arbitrary — it's not live"; the DATA is correct (verified 100/100 stored Monday 2026-10-19 İş Yatırım EOD), the DISPLAY is wrong. Highest-visibility defect in the platform.
- Root cause (planner-verified 2026-10-20, evidence below): **a unit-contract mismatch between the API and the Web formatter, invisible to every existing test layer.**
  1. **The API serves fractions.** `src/Core/Metrics/MarketAggregates.cs:15` documents `ChangePct` as "Daily price change as a decimal fraction (0.05 = +5%)"; the API goldens pin fractions (`MarketEndpointsTests`: xu100 `changePct` **0.02** = +2%, gainer ETA **0.10** = +10%; `MarketSnapshotTests` likewise); the live dev stack serves AGHOL `changePct: 0.014735` (= +1,47%), XU100 `−0.024875`, XU030 `−0.023135` (user-verified via `GET /api/v1/market/overview`). This is consistent with the repo-wide doctrine that %-unit metrics travel as decimal fractions (screener `roe` golden 0.20 = 20%, `ScreenerRunEndpointTests:154`).
  2. **The Web formatter assumes percentages.** `src/Web/src/lib/format.ts:54-66` `formatSignedPercent` — its doc comment claims "the payload's `changePct` is already a percentage, e.g. `2.00` → `+2,00%`" — performs **no ×100**. `src/Web/src/lib/api/contracts.ts:107` repeats the wrong assumption ("`changePct` is already a percentage") on `IndexLevel` (and `MoverEntry` carries it by usage).
  3. **Every `changePct`-class surface is affected** (all flow through `formatSignedPercent` via `ChangeValue`/direct calls in `src/Web/src/routes/MarketOverviewPage.tsx`): index rows (line ~145), movers list + their `aria-label`s (lines ~370/379), and **sector-performance entries** (line ~276 — `sectorPerformance` values are the same fraction class, currently masked only because the real world serves `{}`).
  4. **Why no test caught it:** the Web MSW doubles (`src/Web/src/test/msw/handlers.ts:212-236`) serve **percentage-unit** fixtures (`changePct: 2`, `10`, `-10`) — matching the wrong Web assumption, not the API goldens — so Web unit tests render plausible strings; and the E2E spec (`tests/e2e/src/market-overview.spec.ts:52`) asserts only a sign regex `/[+−-]/` on the index change, never a value. The FU world's snapshot is computed by the real engine from seeded prices, so the E2E stack serves true fractions (0.02) — rendered "+0,02%" — and the sign-only assertion passed anyway.
  5. **Correct already (do not touch):** `marketDivYield` (`formatRatioPercent`, line ~480), all stock-page/screener/DCF percentages (`formatPercent` — fraction-aware). The defect class is exactly the `formatSignedPercent` path.
- **Contract decision (planner-made, recorded): the API stays fraction-unit; the fix is Web-side.** The API's fraction units are pinned by Core docs, all API integration goldens (MOV + screener lanes), real live behavior, and the `03` §4 metric doctrine; flipping the API to percentage units would be a breaking semantic change across every golden for zero benefit. The fix makes the Web layer agree with the served contract — systematically, not spot-patches.
